# Silver Tier Spec — Functional Assistant

**System of record:** `Personal AI Employee Hackathon 0_ Building Autonomous FTEs in 2026.md`
**Constitution:** `AGENTS.md`
**Status:** agreed (Phase 3 interview complete, 2026-08-12)

## Decisions locked in Phase 3

- Second watcher = **Gmail** (filesystem + Gmail = two watchers).
- LinkedIn = **approval + ready-to-post artifact** mode (no live posting; zero account risk).
- Gmail credentials: **build now, user adds creds later**; verify with mock/dry-run tests.
- Email MCP = **custom Python MCP server** (stdio, Gmail API).
- Scheduling = **both cron and Windows Task Scheduler docs**; verify on Linux only.
- Permission boundary = **doc §6.4**: replies to known contacts auto-send; new contacts require approval.

## Goal

Advance the Bronze vault from "watching folders" to a **Functional Assistant**
that watches real communication channels, plans multi-step work, takes
external actions through a dedicated MCP server, and never acts on anything
sensitive without human approval. All of it still runs as Agent Skills.

## User scenarios

- **Morning triage:** New important emails and dropped files sit in
  `Needs_Action/`. The user asks Claude Code to "process the inbox". Claude
  reads each item, writes `Plans/PLAN_*.md` with checkbox steps, completes the
  safe steps itself, and routes anything sensitive (e.g. replying to a new
  contact, posting) to `Pending_Approval/`. The user approves, the action
  executes, and the result lands in `Logs/` and `Done/`.
- **Business post:** Claude drafts a LinkedIn post about the business (from
  `Business_Goals.md` or a draft request), files it under
  `Pending_Approval/`. After the user moves it to `Approved/`, it is published
  to LinkedIn (or, in safe mode, a final ready-to-post artifact is produced).
- **Scheduled operation:** A scheduler wakes the watchers and the dashboard
  updater on a set cadence, so the vault is current without the user
  triggering anything.

## Functional requirements

- **FR1 — Two+ watchers.** The `filesystem-watcher` skill (Bronze) remains.
  A new Gmail watcher skill polls the Gmail account for new unread/important
  emails matching configured criteria and writes one
  `Needs_Action/EMAIL_<id>.md` per new email (frontmatter: `type`, `from`,
  `subject`, `received`, `priority`, `status`, `gmail_id`; body: snippet +
  suggested actions). It never writes a duplicate action file for the same
  message, and it handles missing/expired credentials without crashing
  (dry-run mode).
- **FR2 — LinkedIn business posts.** The system can produce a business sales
  post and, only after human approval, produce the final ready-to-post
  LinkedIn artifact. Drafts are written to `Pending_Approval/LINKEDIN_<date>.md`;
  approval produces `Done/`/`Plans/` artifact with the final post text. No
  live posting is performed (LinkedIn ToS/ban risk out of scope).
- **FR3 — Claude reasoning loop / Plan.md.** A `plan-creator` skill drives
  Claude through: read `Needs_Action/` → write `Plans/PLAN_<task>.md`
  (frontmatter `created`, `status`; checkbox steps with owners) → execute
  steps → mark complete → move the item to `Done/`. The loop is documented as
  the daily operating loop (using `/goal` or repeated invocation); the
  Ralph-Wiggum stop-hook plugin is out of scope (Gold tier).
- **FR4 — One working MCP server (email).** A **custom Python email MCP
  server** is registered with Claude Code and exposes at least `search_email`,
  `draft_email`, and `send_email`. `send_email` never fires directly: it only
  executes for an approval that exists in `Approved/`, except replies to known
  contacts (per §6.4) which auto-send. Drafting and searching work without
  approval.
- **FR5 — HITL approval workflow.** An `approval-workflow` skill standardizes
  sensitive actions: create `Pending_Approval/<ACTION>_<target>.md` (frontmatter:
  `type`, `action`, `target`, `reason`, `created`, `status`), wait for the
  human to move it to `Approved/` or `Rejected/`, then execute (or cancel)
  and log. **Permission boundary (§6.4):** replies to known contacts
  (whitelist in `Company_Handbook.md`) auto-send; new contacts, bulk sends, and
  payments always require approval. Every executed action is appended to
  `Logs/YYYY-MM-DD.json`.
- **FR6 — Scheduling.** A `scheduler` skill plus **cron and Windows Task
  Scheduler examples** run the watchers and the dashboard updater at defined
  intervals. The cadence and commands are documented; Linux cron is verified.
- **FR7 — All AI functionality as Agent Skills.** Every new capability
  (gmail-watcher, linkedin-poster, plan-creator, email-mcp integration,
  approval-workflow, scheduler) ships as a skill with a `SKILL.md`.
- **FR8 — Dashboard reflects Silver state.** `Dashboard.md` (regenerated by
  `dashboard-updater`) shows counts for new items, in-progress items, plans,
  pending approvals, and completed items, plus a recent-events list.

## Edge cases & rules

- Empty inbox / no new items → no action files created; watcher keeps running.
- Duplicate message (re-poll, Gmail push overlap) → deduped; no second file.
- Gmail token expired or API down → watcher logs the error and continues
  without creating files; existing action files are preserved.
- No credentials present → watcher runs in dry-run mode and reports it.
- Known-contact auto-send (per §6.4): whitelist lives in `Company_Handbook.md`
  (or a `known_contacts.json`, gitignored); a reply to a whitelisted address
  sends without an approval file; anything else is gated.
- Approval file never acted on → stays pending, counted on the dashboard,
  never auto-executed.
- Approved email whose target is empty/malformed → logged as failed, never sent.
- LinkedIn publish → produces the ready-to-post artifact instead (no live post).
- Scheduler crash → documented restart via cron/PM2; watchers may queue items.
- Rejecting an approval → action cancelled, logged, item moved to `Done/` with
  a `rejected` note.

## Out of scope (this round)

- WhatsApp watcher (needs browser session + ToS risk) — optional later.
- Facebook/Instagram/Twitter posting, Odoo accounting (Gold tier).
- Cloud 24/7 deployment, vault sync, A2A (Platinum tier).
- Ralph-Wiggum Stop-hook plugin (Gold tier); Silver uses the documented loop.
- Real payment execution (banking credentials); approval scaffolding only.

## Acceptance criteria

- **AC1:** `filesystem-watcher` and `gmail-watcher` both run; a new email
  produces exactly one `Needs_Action/EMAIL_<id>.md` and re-polling creates no
  duplicates.
- **AC2:** A business post is drafted to `Pending_Approval/`; after the user
  moves it to `Approved/` a final ready-to-post LinkedIn artifact is produced
  (no live posting).
- **AC3:** Pointing Claude at `Needs_Action/` via `plan-creator` produces
  `Plans/PLAN_*.md` with checkboxes, and a completed plan moves its item to
  `Done/`.
- **AC4:** The custom Python email MCP server is discoverable by Claude Code
  with `search_email`/`draft_email`/`send_email` tools; sends only happen for
  a matching `Approved/` approval or a known-contact auto-send.
- **AC5:** Every sensitive action goes through `Pending_Approval/` →
  `Approved/`/`Rejected/` and is logged in `Logs/`; known-contact replies
  auto-send.
- **AC6:** The scheduler skill plus cron and Windows Task Scheduler examples
  run watchers + dashboard on a documented schedule (Linux verified).
- **AC7:** All new functionality exists as Agent Skills under `.claude/skills/`.
- **AC8:** `Dashboard.md` shows silver-tier counts after running
  `dashboard-updater`.
